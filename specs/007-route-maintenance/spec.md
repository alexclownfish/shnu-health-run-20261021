# Feature Specification: 路线与点位更换方法

**Created**: 2026-10-09
**Branch**: 沿用 `theme/warm-orange-indigo`
**Status**: 2026-10-11 用户授权实施最新 KMZ 路线
**Input**: 最初解释路线维护方法；2026-10-11 用户提供完整 KMZ 并明确要求开始开发，把新轨迹作为小程序地图。

## User Scenarios & Testing

### User Story 1 - 替换路线与三个任务点 (Priority: P1)

活动组织者提供新路线和点位资料，能够知道需要更新哪些配置、二维码和发布资料。

**Independent Test**: 核对地图包含完整 357 点、两段轨迹、原始起终点及三个照片标注，完成严格起点→三站扫码/照片→终点流程。

**Acceptance Scenarios**:

1. 轨迹或点位位置变化时，同步路线线条、起终点、任务点标记和距离展示。
2. 三个任务点的名称或照片要求变化时，同步点位配置，不改变原有打卡顺序规则。
3. 新活动使用独立标识和二维码时，说明本机旧进度与云端名单的隔离方法。

### User Story 2 - 新旧路线记录隔离 (Priority: P1)

用户更新后新路线从起点重新开始，旧进度和照片不被删除或算进新成绩。管理员按新活动及路线版本导出，旧上报队列不被重标为新路线。

**Independent Test**: 预置旧 v3 本机记录，确认新路线为空且旧数据未写改；新旧活动目标的上报队列互不混入。

### Edge Cases

- 不同坐标来源不能重复转换；轨迹往返时不能仅按最近坐标决定点位顺序。
- 起终点目前取轨迹首尾点，无法通过修改名称单独移动。
- H5 预览与真机地图不同；不能据 H5 背景判断地理位置正确。
- 小程序旧进度不会因 routeVersion 改变自动隔离。
- 云端名单按活动和用户去重；仅更新路线版本不等于新建独立活动名单。

## Requirements

- **FR-001**: 解释现有原生地图和 H5 绘图的实际实现，不新增平台能力承诺。
- **FR-002**: 提供 GPX、坐标来源、起终点、三个任务点、照片要求及二维码的输入与修改清单。
- **FR-003**: 说明固定三点限制、本地进度与可选云端汇总的联动。
- **FR-004**: 区分当前可用的人工配置方法与建议的后续维护工具，不把建议描述为已实现。
- **FR-005**: 将完整 KMZ 的轨迹与点位接入现有原生地图，保留两段边界及标注精确坐标；通过原 WGS84 → GCJ-02 路径输出，最终真机核对坐标。
- **FR-006**: 活动总里程显示 3.50 公里，三站累计里程仍来自同一条路线；H5 使用共享总里程和分段数据。
- **FR-007**: 保持三个任务点、照片上传和五张二维码 payload；不修改主题与其他业务规则。
- **FR-008**: 新路线使用独立本机存储和路线标识，保留旧存储；开发名单使用独立 activityId 和 routeVersion，不覆盖旧名单。
- **FR-009**: 同步本地云函数/导出示例配置，提供部署说明；不自动部署云环境，不启用正式汇总。

## Success Criteria

- 两种地图的来源和五个检查点的映射均有明确说明。
- 同数量换点、改变数量、二维码复用及活动隔离四种情况均给出处理方法。
- 验收包含坐标、路线顺序、扫码计时、旧数据和开发环境名单。

## Assumptions

KMZ 和三个标注已齐全，任务点仍为三个，扫码拍照及二维码沿用现有配置。此次接入代码和离线预览，地图位置、现场扫码和开发云配置仍须体验版验收。
