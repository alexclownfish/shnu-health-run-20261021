# Feature Specification: 暖橙靛蓝视觉主题

**Feature Branch**: `003-warm-orange-indigo-theme`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: 基于参考图，将小程序现有绿色 UI 换成暖米白、橙色、靛蓝和珊瑚色主题，保持业务逻辑不变，先通过 Spec Kit 产出设计方案。

## User Scenarios & Testing

### User Story 1 - 浏览活动路线与点位 (Priority: P1)

用户打开活动首页，可以在暖米白背景、橙色活动主视觉和靛蓝行动按钮中快速识别路线、当前进度和下一步操作。

**Why this priority**: 活动首页是所有用户的第一入口，也是主题识别最集中的页面。

**Independent Test**: 在未完成、进行中和已完成三种本地进度下打开路线页，确认布局、文案、地图、点位顺序和按钮行为与当前版本一致，仅视觉颜色发生变化。

**Acceptance Scenarios**:

1. **Given** 用户尚未完成任何点位，**When** 打开路线页，**Then** 页面显示暖米白底、橙色路线主卡、靛蓝主按钮和清晰的当前点位状态。
2. **Given** 用户已完成部分点位，**When** 返回路线页，**Then** 已完成、当前和锁定状态使用不同的主题色层级表达，点位顺序和点击行为不变。
3. **Given** 用户点击当前点位或主按钮，**When** 进入打卡页，**Then** 导航路径与当前版本一致。

### User Story 2 - 完成扫码与照片流程 (Priority: P1)

用户在扫码打卡和照片保存过程中，可以通过橙色强调、靛蓝操作色和明确的珊瑚色错误色识别当前状态。

**Why this priority**: 这是活动核心流程，必须在换肤后保持状态可读且不能误导用户。

**Independent Test**: 依次验证等待扫码、扫码中、扫码成功、扫码失败、照片未选择和照片保存成功状态，确认颜色改变不影响流程转移。

**Acceptance Scenarios**:

1. **Given** 当前点位等待扫码，**When** 用户进入打卡页，**Then** 页面显示靛蓝扫码视觉和橙色/暖色辅助区域，不出现旧绿色主视觉。
2. **Given** 用户扫描正确二维码，**When** 校验通过，**Then** 成功状态使用靛蓝或黄色高亮，并直接进入照片上传页。
3. **Given** 用户扫描错误点位或二维码无效，**When** 校验失败，**Then** 错误状态使用珊瑚色，文案和重试行为保持不变。
4. **Given** 用户扫码成功并选择照片，**When** 保存点位，**Then** 提交按钮、进度条和成功弹层使用同一套主题色语义，数据保存行为不变。

### User Story 3 - 查看记录、个人中心与完赛凭证 (Priority: P2)

用户查看运动记录、个人中心和完赛凭证时，可以感知同一套活动品牌主题，并清楚区分完成、锁定、提示和危险状态。

**Why this priority**: 这些页面承担复盘和分享价值，统一视觉可以提升完整度，但不阻塞核心打卡。

**Independent Test**: 打开记录、个人中心和完赛凭证页面，覆盖空状态、部分完成和全程完成状态；确认保存凭证生成的图片也使用同一套主题色。

**Acceptance Scenarios**:

1. **Given** 用户没有历史记录，**When** 打开记录页，**Then** 空状态与背景、边框和次要文本保持足够对比度。
2. **Given** 用户完成部分或全部路线，**When** 打开个人中心或完赛凭证，**Then** 进度、徽章、完成状态和操作按钮沿用暖橙靛蓝主题。
3. **Given** 用户保存完赛凭证，**When** 图片生成完成，**Then** 图片中的颜色与页面主题一致，不回退到旧绿色。

## Edge Cases

- 绿色旧变量仍被某个页面、组件、地图标记或 Canvas 绘图引用时，必须在发布前被发现并处理；不能只修改 `app.wxss` 后宣称换肤完成。
- 靛蓝主按钮、橙色主视觉和珊瑚色错误状态在低亮度屏幕及浅色背景上必须保持可读，不得出现白字与浅色背景对比不足。
- disabled、locked、empty、success、error 等状态必须有独立且稳定的视觉层级，不得只依靠颜色区分。
- 地图底图由微信原生组件提供，主题只控制路线线条、标记、提示浮层等自有元素，不修改地图坐标、路线数据或点位点击逻辑。
- 系统导航栏、底部 TabBar、完赛 Canvas 与 WXSS 页面颜色不一致时，应以主题 token 为准统一处理。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 将小程序自有 UI 的绿色主色替换为暖橙、靛蓝、珊瑚和暖中性色组合，保留页面结构、文案、尺寸和交互行为。
- **FR-002**: 系统 MUST 建立一套集中定义的主题 token，至少覆盖页面背景、卡片、主文字、次文字、边框、主操作、主视觉、完成、错误、警告和禁用状态。
- **FR-003**: 系统 MUST 让路线页、扫码页、照片页、记录页、个人中心页和完赛凭证页使用同一套主题语义。
- **FR-004**: 系统 MUST 将组件 `route-map` 的路线、点位、起点和状态颜色纳入主题审查，且不得改变地图数据和点击行为。
- **FR-005**: 系统 MUST 将完赛凭证 Canvas 绘图中的旧绿色、薄荷色和荧光绿色替换为对应主题色，页面预览与保存图片保持一致。
- **FR-006**: 系统 MUST 更新微信导航栏、底部 TabBar 和页面背景配置，使其与主题背景和主操作色一致。
- **FR-007**: 系统 MUST 保持扫码校验、路线顺序、本地进度、拍照保存、完赛凭证生成及所有状态转移不变。
- **FR-008**: 系统 MUST 保持所有现有业务自动化测试通过，并增加颜色 token、旧绿色残留扫描和关键状态可见性的检查。
- **FR-009**: 系统 MUST 对主按钮、错误状态、完成状态和禁用状态进行浅色背景对比度检查；状态不能只依靠颜色表达。

### Key Entities

- **主题 Token**: 代表一组具有语义的颜色值，而不是页面私有颜色；包括背景、内容、操作、状态和装饰类别。
- **页面状态**: 现有业务页面的等待、进行中、成功、错误、锁定、空状态和完成状态；主题只改变其呈现，不改变状态转换。
- **生成凭证图**: 由现有 Canvas 绘制的本地完赛图片，必须与页面使用同一套颜色语义。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 7 个业务页面、2 个自有组件、应用导航配置和完赛 Canvas 完成主题覆盖，发布包中不再出现旧绿色主色的自有 UI 引用。
- **SC-002**: 核心路线、扫码、照片和完赛流程的现有自动化测试 100% 通过，且不新增业务状态或接口。
- **SC-003**: 在 320px 至主流手机宽度范围内，换肤后无文字遮挡、按钮溢出、底部操作被安全区遮挡或状态文案不可读。
- **SC-004**: 关键主按钮、错误提示、完成提示和禁用按钮在浅色背景上通过人工视觉检查，不出现白字与背景融合的情况。
- **SC-005**: 页面预览与保存的完赛凭证在主题色、背景色和完成状态色上保持一致。

## Assumptions

- 本次只做视觉主题迁移，不新增后端、数据字段、页面、业务规则或平台分支。
- 参考图中的插画和设备边框不作为本次必须新增的图片资产；优先复用现有 CSS 几何装饰，仅调整其颜色。
- 地图底图仍由微信原生 `map` 组件渲染，无法由主题完全控制的第三方地图颜色不纳入“旧绿色残留”判定。
- 主题第一版采用暖米白、橙色、靛蓝、珊瑚和黄色，不使用绿色作为主色、成功色或装饰色。
- 当前活动仍是低风险、设备本地状态模式，视觉迁移不改变其数据丢失和不可恢复边界。
